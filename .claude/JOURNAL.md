9. **Task - Fix fish shell cwd detection** (v1.0.16): Fixed "CWD Not Available" error when using fish shell in terminal<br>
   **Result**: The original `_get_child_pid()` method only found the first child process, which could miss the actual shell when fish or other shells have complex process trees. Updated `_get_process_cwd()` to try the direct pty pid first, then iterate through all child candidates until a valid cwd is found. Added `_try_get_cwd()` helper method for cleaner separation. Files modified: `handlers.py`. Version auto-bumped to 1.0.16 during build

10. **Task - Fix mc subshell cwd detection** (v1.0.18): Fixed cwd detection when running Midnight Commander with subshell enabled<br>

Process candidates now sorted by depth descending with shells prioritized at each level, ensuring deepest shell (mc's subshell) is tried first. Files modified: `handlers.py`

12. **Task - Fix cwd detection with deep process trees** (v1.0.22): Fixed "Show in File Browser" returning wrong path when claude or other tools with complex process trees run in terminal<br>
    **Result**: Root cause was the "deepest shell first" algorithm in `_get_process_cwd()`. When claude runs in a terminal, it spawns MCP servers (Playwright, Context7, etc.) which create deep process trees including Chrome processes whose cwd is nonsensical (`/proc/*/fdinfo`). The handler picked Chrome at depth 8 instead of the fish login shell at depth 0. Kept the recursive deepest-first traversal (so mc subshells and similar still work) but added `_is_valid_cwd()` validation that rejects pseudo-filesystem paths (`/proc/*`, `/sys/*`, `/dev/*`) and non-existent directories. The algorithm now recurses the full tree but skips nonsense paths, naturally falling through to the login shell when all deeper processes have invalid cwds. Added 6 tests for `_is_valid_cwd` and updated `TestGetProcessCwd` with mock-based tests for both the Chrome-filtering and file-manager-subshell scenarios. Files modified: `handlers.py`, `tests/test_handlers.py`

15. **Task - Fix terminal cwd resolution** (v1.0.25): Fixed "Show in File Browser" resolving to the wrong project when `claude` runs inside the terminal<br>
    **Result**: Root cause - a shared claude-code daemon (`/tmp/cc-daemon-*`) grafts OTHER terminals' sessions into this terminal's descendant process tree, so the prior deepest-shell-first walk returned a foreign project's (valid) cwd and no validation caught it. Replaced the whole tree-walk + shell-sort + TTY-filter stack in `handlers.py` with the kernel's foreground process group (`tpgid`, field 8 of `/proc/{pid}/stat`), read from the pty shell and resolved via `/proc/{tpgid}/cwd` with a validated pty-pid fallback. A foreign session lives on another pty and can never be this pty's foreground group, so the bug cannot recur; mc-subshell navigation is preserved. Deleted 5 helper methods (~110 lines), dropped a stale `environ` PWD fallback and an info-leaking 500 body. Survived a two-round architect + bug-hunter adversarial review; 21 tests pass, verified live

16. **Task - Recover deleted terminal cwd** (v1.0.26): Fixed "CWD Not Available" for a terminal whose shell sits in a since-deleted directory<br>
    **Result**: Root cause - the terminal's fish login shell (and the `claude` in it) were cd'd into a directory that had been `rm`'d, so `/proc/{pid}/cwd` reads as `<path> (deleted)` and no longer exists. The v1.0.25 `tpgid` resolver correctly rejected the dead path via `_is_valid_cwd` but then returned `None`, surfacing the frontend error. Added a last-resort fallback in `handlers.py`: when both the foreground (`tpgid`) and pty-shell cwds are gone, `_get_recovered_cwd` reads the raw `/proc/{pid}/cwd` link (which survives deletion, unlike an existence-guarded read) and `_nearest_existing_dir` strips the ` (deleted)` suffix and walks up to the closest ancestor that still exists. General for any deleted-cwd terminal; adds no tree-walk and no foreign-session risk. 26 tests pass, both the deleted and live cases verified against real pids
